0. 摘要

本截帧的 UI 由 Unity UGUI（Canvas 批渲染）实现，绘制在全分辨率合成目标（2558×1438）上；3D 场景实际以 2132×1198（≈0.83×）渲染后经泛光合成 pass 上采样，UI 则以原生分辨率叠加（场景低清 + UI 原生的混合策略，详见第 2、7 节）。文字渲染采用 「单通道 R8 动态字体图集 + 统一 UI Shader」方案：截帧中存在两张字体图集（2048×2048 和 1024×1024，均为 R8_UNORM 单通道），即纹理浏览器里看到的那张「密密麻麻」的字形大图。它的作用是：

  • 字形位图缓存：TTF 字形首次使用时按需光栅化并紧密打包进图集，之后每帧直接以纹理 quad 采样，避免重复光栅化；
  • 合批基础：同一图集 + 同一材质的多个 Text 合并为少量 draw call（本帧 10 个文字 draw 共约 354 个字形 quad，最大单 draw 合并了 180 个字形）；
  • 省内存/带宽：每像素仅 1 字节（alpha-only），文字颜色完全由顶点色 × tint 决定，与 RGBA 图集（4 字节/像素）相比省 75% 显存。

GPU 侧文字渲染成本极低（10 个 draw 合计约 0.106ms）；UGUI 的开销主要在 CPU 侧（Canvas 网格重建），GPU 侧不构成瓶颈。

3. UI 渲染实现（UGUI 取证）

3.1 共享 Canvas 网格缓冲

UI draw 大量使用 glDrawElementsBaseVertex，且 base_vertex/index_offset 持续递增（如文字 draw 5886 的 base_vertex=52、index_offset=78；pass 末尾的 9252 base_vertex=9943、index_offset=21576）。这是 Unity UGUI 的标志性实现：整个 Canvas 的所有图元写入同一块大顶点/索引缓冲，各 UI 元素按区间切分绘制，CPU 每帧重建网格，GPU 只按区间消费。

3.2 顶点格式与统一 Shader

UI 顶点输入（从 SPIR-V 还原）：position(float4) + color(float4) + uv(float2)，即 UGUI 标准的「位置 + 顶点色 + UV」。帧内 Sprite（RGBA 图集）与文字（R8 图集）共用同一个 UI Shader（ResourceId::16186 / 16187）：

Shader 端Uniform（$Globals）含义
Vertex（16186）_u_Color / unity_MatrixVP / unity_ObjectToWorldtint 颜色 + Canvas→裁剪空间变换
Pixel（16187）_u_ClipRect（vec4）RectTransform 裁剪矩形，PS 内做 4 边硬裁剪，因子乘进 alpha
Pixel（16187）_u_TextureSampleAdd（vec4）字形打包补偿常数（Unity UI/Default Font 同款机制）

3.3 像素着色器逻辑还原（对应 Unity「UI/Default Font」）

// 事件 5886，Pixel Shader 16187，SPIR-V 反编译还原
float4 clip = step(_u_ClipRect.xy, pos.xy) * step(pos.xy, _u_ClipRect.zw);   // 矩形硬裁剪
float  clipFactor = clip.x * clip.y;                                    // 0 或 1
float4 tex = texture(_u_MainTex, uv);                                  // R8 字体图集（经 swizzle，alpha=字形覆盖度）
float4 col = (tex + _u_TextureSampleAdd) * vColor * _u_Color;          // 字形 × 顶点色 × tint
col.a *= clipFactor;                                                      // 裁剪只压 alpha
SV_Target0 = col;

每字形单次采样、单 quad（2 三角形/6 索引），没有描边多次采样 —— 描边/发光等效果在图集内预先烘焙或直接不使用。文字颜色完全来自顶点色，这正是图集可以用 R8 单通道的原因。

4.2 为什么「密密麻麻」—— 动态字体的工作方式

这是 Unity 动态字体（Runtime Font Atlas）的运行时图集，其填充逻辑决定了它必然长得密密麻麻：

  1. 按需光栅化：文本首次需要某字形时，才从 TTF/OTF 光栅化当前字号的位图，然后紧密打包（无排序、无间隙）进图集空闲区域；
  2. 汉字集巨大：中文常用字数千个（GB2312 共 6763 字），局内文本（英雄名、装备、伤害数字、技能描述…）在一局游戏里累计触达的字形会持续堆积；
  3. 字号/样式碎片：同一字体的每种字号、加粗、描边变体都是独立位图，全部堆进同一张图集；
  4. 只增不减：图集在会话内从不回收字形（直到写满重建），所以长时间游玩后看到的图集几乎无空隙 —— 即截帧中观察到的效果。

两张图集并存，对应两个不同的字体（典型如：正文/中文字体 2048² + 数字/标题等专用字体 1024²），各自独立维护动态图集。

4.3 图集在渲染管线中的三重作用

  • 缓存 字形位图缓存：光栅化结果复用，避免每帧对每个字做 TTF 曲线填充；文字 = 普通纹理 quad。
  • 合批 合批的钥匙：同图集 + 同材质 ⇒ UGUI 可把多个 Text 合并成一个 draw。证据：6194 单个 draw 承载 180 个字形（1080 索引）；当文字被裁剪矩形、图集切换、渲染顺序打断时才拆分为新 draw —— 这解释了为何 274 个字形拆成 7 个 draw。
  • 省资源 内存/带宽优化：R8 单通道 1 字节/像素（对比 RGBA 图 4 字节/像素），采样带宽同样减 75%；颜色信息零存储，由顶点色实时提供。

6. 优化建议

  1. 显存 动态图集膨胀风险：2048² R8（4MB）+ 1024² R8（1MB）常驻；图集写满会触发整图重建（新分配 + 重新上传 4MB + 全部字形重光栅化），在低端机上表现为偶发卡顿尖峰。可对局内固定文案（技能名、固定 UI 词）使用静态烘焙字库子集，仅动态数字走动态字体。
  2. CPU Canvas 重建开销才是 UGUI 主成本：伤害跳字、倒计时等每帧变化文本会持续重建网格（见 base_vertex 持续增长的共享大缓冲）。建议把高频变化文字拆到独立 Canvas/子层级，避免整 Canvas 重算。
  3. 合批 已有良好实践（180 字形合入单 draw），保持「同字体、同图集、同层级」可进一步减少 10 个文字 draw 的拆分（拆分源于 ClipRect/穿插的 Sprite）。
  4. 进阶 若需彻底压缩图集显存：SDF/TextMeshPro 方案可用一张小图集覆盖全部字号（签名距离场缩放），代价是 PS 稍复杂。

7. 附加发现：「画面渲染两次」的真相 —— 场景渲染提前一帧（render-ahead）

初版报告曾把帧尾的第二轮场景渲染（EID 6713~9219，写入 RT 80804）误判为「疑似无泛光下遗留的冗余重绘」。二次取证后结论反转，证据链如下：

  1. 80804 是主场景 RT，且每帧窗口内「先被消费、后被重写」：5797/5820（帧开头）把它作为 _u_BloomSrcTex/_u_BloomTex 上采样合成到 17893；随后 7116 清空、7138~9219 重新渲染整个场景进同一 RT。第二轮的输出在本帧内没有任何消费者（全帧 508 个 draw 反查，80804 的采样者仅 5797/5820）→ 只能被下一帧消费。
  2. 两轮绘制序列逐条对齐，但内容状态不同：两轮 draw 序列前 35+ 项完全一致（72, 39, 4704, 1068, 13272, 4290, 1995, 9723, 6216, 2064, 3708, 3432, 228, …），是同一套场景管线；但特效段出现粒子四边形数量漂移（对齐位置上 54→48、60→54 quads），且第二轮比第一轮少了约 150 个特效 draw → 第二轮的 draw list 是用更晚的游戏状态（特效已衰减/结束）构建的，即下一帧的状态。
  3. 结构完全对称：第二轮也带自己的 CSM 阴影（Depth-only #2）与中间 RT pass（Colour #6），构成完整的「下一帧场景流水线」；但没有 UI、合成与 present —— 它只是下一帧的「场景部分」提前提交。

结论：引擎做了场景渲染提前一帧提交的流水线化设计——第 N 帧的命令窗口内（present 之前）就已提交第 N+1 帧的场景渲染。RenderDoc 以 present 划分帧边界，所以截帧里看起来像「一帧渲染了两遍场景」。收益：GPU 在 CPU 构建 N+1 帧的 UI/逻辑期间就开始执行下一帧场景，缩短 present 到 present 的关键路径。显示内容上场景(N) 与 UI(N) 出自同一游戏状态（场景在 N-1 窗口渲染、UI 在 N 窗口渲染），不引入额外显示延迟。

关于「多线程改造」的推断：截帧只能证明命令层面的提前提交（资源读写顺序 + 内容状态漂移），无法证明线程拓扑——RenderDoc 捕获的是串行化后的命令流，线程/提交者信息已丢失。「main / render / cmd 提交线程」的三线程结构是合理推测但不可从截帧证实；且本截帧为 OpenGL（非 Vulkan），单上下文命令本身即串行，提前提交是调度设计而非并行执行。
