级联截帧失效分析（2026-10-26 14:41 MuMu 会话）

结论：级联截帧没有"功能退化"，而是根本没跑到 fork 的代码——目标进程 MuMuNxDevice.exe [PID 25544] 被官方 RenderDoc 与 fork rendertest 双重注入， 官方 build 抢先占有了全部 GL/Vulkan 设备和该 PID 的 target-control 通道。14:41 的 10 次截帧实际全部由 官方 build 的 GL driver 执行（官方代码里没有级联逻辑），所以只产出单份 GL 上屏帧（~103MB）， 没有 Vulkan 游戏真帧 capture.rdc，fork 侧日志连一行 Cascade bridge diagnostics 都没有。

三、失效根因链

官方 qrenderdoc 以管理员启动（14:25:56）
  ├─ ① 重新启用官方 renderdoc.json 注册 → fork 启动时的自修复被覆盖
  │     （HKLM ImplicitLayers 三家同名 VK_LAYER_RENDERDOC_Capture 全部启用，loader 去重结果不可控）
  └─ ② 抢先 attach MuMuNxDevice [25544]（14:27:06，进程启动级注入）
        ├─ GL：官方 dll 先 hook WGL，全部上下文注册进官方表
        ├─ Vulkan：loader 选官方 layer，设备注册进官方表（= 9-28 根因复发）
        └─ target-control 通道被官方 dll 先绑定
fork rendertest.dll 晚 62s 注入（14:28:08）
  └─ 进程内 capturer 表全空（app 日志无任何 Adding/Cascade 行）
qrendertest UI 触发截帧（14:41）
  └─ 消息送达官方 dll 的 target-control → 官方 GL driver 执行
       └─ 官方代码无级联逻辑 → 单份 GL 上屏帧 ×10，Vulkan 游戏真帧丢失

与 2026-09-28 文档（级联截帧分析.html / util/mumu-capture/README.md） 的"同名 Vulkan layer 抢注"同族，本次叠加了两个新变种：

  • 官方 UI 直接抢先 attach 了同一目标进程（GL 侧也被抢，不只 Vulkan）；
  • target-control 通道先到先得，qrendertest UI 的触发消息实际送进了官方 dll—— 所以连 fork 的级联代码都没被执行，排查时 fork 日志"干净"得具有迷惑性。

四、处置（恢复级联）

  1. 关闭官方 qrenderdoc 实例（pid 16280）；截 MuMu 期间不要再开官方 UI——它每次以管理员启动都会重新注册自己的 layer。
  2. 以管理员重启 qrendertest：fork 启动自修复（qrenderdoc.cpp main → RENDERDOC_UpdateVulkanLayerRegistration(true)）会把 renderdoc.json / epcat.json 等冲突注册禁用；确认 CaptureDialog 警告条消失（非管理员启动会静默失败）。
  3. 完全重启 MuMu：已注入进程的官方 dll 无法卸载，必须重启目标进程。
  4. 只用 qrendertest 一家 attach 目标。

六、永久修复方案（三处单点改动 + 一条纪律）

三处失效环节在 fork 代码里各有单点开关，全部改掉后该问题不再可能静默复发：

#改动位置根治什么
1fork 的 Vulkan layer 改名 VK_LAYER_RENDERDOC_Capture_RT，启用环境变量改名 ENABLE_VULKAN_RENDERTEST_CAPTURErenderdoc/common/globalconfig.h（RENDERDOC_VULKAN_LAYER_NAME / RENDERDOC_VULKAN_LAYER_VAR）+ renderdoc/renderdoc.vcxproj 两个 PropertyGroup 的 <VulkanLayerName>/<VulkanEnableVar>（构建时 stamp 进 rendertest.json）注册表同名互斥。改名后官方与 fork manifest 可共存，loader 不再二选一；fork 注入时 hook 强制启用自己的 layer 名（vk_device_funcs.cpp:120/618 走同一常量），官方 layer 因启用变量名不同在 fork 进程里永远休眠 → Vulkan 设备确定性地注册进 fork 的表
2target-control 协议号改为 fork 专属值（如 109，仅接受 109）renderdoc/core/target_control.cpp:36 TargetControlProtocolVersion / IsProtocolVersionSupported"静默连错服务端"。rendertest UI 再连到官方 dll 时握手即拒绝，双注入从"抓出错的文件"变成"显式报错"
3target-control 端口段迁移（38920 → 48920）renderdoc/common/globalconfig.h:143 RenderDoc_FirstTargetControlPort进程发现层隔离。UI 枚举时探测不到官方 dll 的端口段，attach 列表里根本不会出现官方注入的进程；同进程双注入时两 dll 也不再抢 38920

配套纪律：官方 qrenderdoc 不要以管理员运行（非管理员写不了 HKLM，无法复活其 layer 注册）； 最好直接卸载官方 RenderDoc 与 EPCat（epcat.json 是第三个同名 layer 注册者）。改名后这些不再是必需，但仍建议保持。

可选加固：fork core 初始化时 GetModuleHandleA("renderdoc.dll") 非空即 RDCWARN 并在 handshake 上报—— GL 侧"谁先注入谁赢"无法从注册表根治，显式告警是底线。

改名注意：json 里 VK_LAYER_RENDERDOC_CaptureGetInstanceProcAddr 等导出符号名不要动 （它们只是 dll 导出函数名，不是 layer 身份）；Android 路径（android.cpp 的 gpu_debug_layers）走同一常量自动跟随。
