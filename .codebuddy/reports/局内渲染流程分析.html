二、逐 Pass 分析

1. Depth-only Pass #1 方向光阴影图 EID 203–316 · 11 次绘制

输出目标D16 1024×1024 深度图（184522），无颜色目标
判定依据VS 常量含 _ug_ShadowPancaking、_ug_OrthoCamera、_ug_DepthBias、_ug_ShadowNearClipPlane → 正交阴影相机 + 深度偏移，典型 Unity 方向光 shadow map（含 pancaking 优化）
内容10 个投影物：棋盘地形（27585 / 21885 idx）、英雄（8352 / 8235 / 10338 idx）、2×798 idx 小物件等
备注首尾 glInvalidateFramebuffer：tile-based GPU 上放弃旧内容，移动管线常规操作

2. Colour Pass #1 角色贴地投影 RT EID 322–632 · 42 次绘制

输出目标R8_UNORM 512×512（69250）
红色 Clear(1,0,0,1) —— 单通道阴影 mask，R=1 表示"无阴影"，英雄投影区域压暗
判定依据PS 常量 _u_ProjectorShadowStrength、_ug_HeroShadowIntensity；VS _ug_ShadowExpandScale → 王者荣耀系的角色贴片假阴影（projector blob shadow）
内容42 个 draw 与 Depth-only #1 中的角色网格一一对应（把棋子/英雄画进投影图）

3. 游离 Draw 投影图后处理 EID 650 · 1 次绘制

  • 采样 69250 → 输出到相邻的 R8 512×512（69251），6 索引全屏 quad
  • 对投影 mask 做一次 blur / 展开，供主场景中英雄/地面采样

4. Colour Pass #2 主场景 EID 656–6202 · 289 次绘制（全帧 DC 大头，约占游戏帧 60%）

输出目标R8G8B8A8 2132×1198（69655）+ 深度（69656）。动态分辨率：仅为窗口 2558×1438 的 83.3%
Clear灰蓝底色 (0.498, 0.518, 0.565) + 深度 + 模板

内部结构

  • 背景：开头 1 个 6-idx quad（天空盒/背景）
  • 大网格：棋盘地形 56508 / 56208 idx（带 512² lightmap + 雾效 _ug_FogParam + _ug_EnableBlurReflection）、62298 / 28824 / 27942 / 21915 idx 场景件
  • 英雄棋子：一批 ~9000 idx 的 draw。相同索引数成对出现是棋盘上两个相同棋子（自走棋同卡多张），不是重复渲染。 英雄 shader 很重：Fresnel 边缘光、受击变色 _u_HurtColor、金属度/粗糙度 remap、Glow、玩家配色 _u_PlayerId 等 22+ 个 PS 常量
  • 中后段：大量 glDrawElementsBaseVertex 小 draw（特效、召唤物、小兵）和成组的 2628 idx ×4（粒子批次）

5. Colour Pass #3 – #18 Bloom 金字塔 EID 6203–6528 · 16 个全屏三角形

  • 每个 pass 仅 1 个 3-索引全屏三角形，逐级降采样：533×299 → … → 16×9 → 8×4
  • 第一级（EID 6219，45µs）为链上最贵，是 bright-pass / 首级降采样
  • 随后逐级上采样回 533×299（184525），供合成阶段使用
  • 16 级 ≈ 1 级 bright-pass + 7 级 down + 8 级 up，标准 Bloom 金字塔

6. Colour Pass #19 后处理合成 + UI EID 6541–7805 · 125 次绘制

输出目标R8G8B8A8 2558×1438（3283）+ 深度（3284）
合成EID 6544 全屏三角形采样：场景 69655（2132×1198）+ Bloom 结果 184525 + 自动曝光纹理（16×16，_u_AutoExposureEnable）—— 合成与上采样合一，直接放大到窗口分辨率
UI清深度/模板后画 123 个 UI 元素：绝大多数是 6-idx quad（血条、头像、按钮、伤害数字），少量大的（2430 idx 的小地图/文本批次等）
结尾glFinish()（1.49ms）—— 游戏侧渲染结束，等待 GPU 排空

7. Copy/Clear Pass #1 外壳合成器拷贝 EID 7832–7847

  • 全屏 blit：Texture 1580（2558×1438，上一帧的合成结果，本帧无人写它）→ 3282（同尺寸）
  • 后跟 3 个 glFlush

8. Depth-only #2 / Colour #20 / EID 8569 / Colour #21 下一帧的开头（截帧跨帧） EID 8122–10123 · ~125 次绘制

  • 阴影图（11 draw）、角色投影（42 draw，与 Pass #1 完全一致）、投影 blur（8569）、主场景不透明部分（70 draw，写入同一个 69655）
  • 这是下一帧的内容被卷入本次截帧，分析 DC 时应剔除

9. Colour Pass #22 + 帧尾 外壳上屏链 EID 10145–10255

  • 清黑 → EID 10185：采样 3282，经 _usk_RTAdjust + _uumatrix_S1_c0 旋转矩阵写入 Texture 153（1440×2560 竖屏）—— 横屏游戏画面转竖屏手机屏幕
  • 清黑 → EID 10245：采样 153，带 _uu_brightness / _uu_gamma（亮度/伽马调节）画到 EGL backbuffer
  • SwapBuffers present
  • 其中夹杂 10214 / 10251 两个 9000-idx 游戏 draw（下一帧场景继续提交，与合成器交错）

三、整体渲染流程图

[游戏帧 N] 阴影图 1024² D16 (11DC) → 角色投影 512² R8 (42DC) → 投影 blur (1DC) → 主场景 2132×1198 (289DC，83.3% 动态分辨率) → Bloom 16 级金字塔 (16DC) → 合成 + 自动曝光 + 上采样 2558×1438 + UI (125DC) → 3283 ← 本帧成果，留给下次 present [外壳合成器，呈现帧 N-1] 1580 → 3282 → [旋转] 153 (1440×2560) → [亮度/伽马] Backbuffer → SwapBuffers [游戏帧 N+1 已开始（本截帧的尾部）] 阴影图 → 角色投影 → 场景不透明部分 (~123DC，属下一帧)

四、主要观察与优化建议

1. Present 延迟一帧

本帧渲染成果 3283 在本帧无人读取，上屏的是上一帧的 1580 —— 游戏到显示有固定 1 帧延迟（外壳投屏架构所致）。

2. 动态分辨率

场景按 83.3% 渲染（2132×1198），合成时一次性上采样到 2558×1438，省了全分辨率渲染的开销，做法合理。

3. 同步点气泡

EID 656 invalidate 等待 10.8ms、8575 等 3.3ms、6541 等 2.8ms、glFinish 1.49ms + 帧尾 glFlush 1.97ms。 游戏渲染线程与外壳合成器在同一 GL 上下文交错提交（glFinish / glFlush 为分界），存在明显的 CPU-GPU 串行化，是帧时间的主要损耗点。

4. 上屏链冗余

一帧 4 次全尺寸全屏 blit（合成→3283、1580→3282、3282→153、153→backbuffer），其中 3282 这一跳是同尺寸纯拷贝，理论上可省。

5. 双轨阴影

阴影方案为 "1024² 方向光 shadow map + 512² 角色贴片投影" 双轨，投影图还多做一次全屏 blur（69250→69251），可考虑合并。

6. DC 分布

主场景 289 DC 占游戏帧约 60%，其中英雄棋子 ~9000 idx 成对出现属于同卡多张棋子（非重复渲染）； UI 123 DC 以 6-idx quad 为主，有合批空间。

五、泛光（Bloom）动态开关对比

对比截帧：局内-有泛光.rdc（rendertest 实例） vs 局内-无泛光.rdc（renderdoc 实例）。 另：本文档主体分析的 局内-战斗-OpenGL.rdc 也属于「有泛光」形态。

对比项有泛光无泛光
后处理链16 级全屏 pass（Colour Pass #3–#18）仅 1 级全屏 pass（Colour Pass #4，EID 5797）
链第一级（bright-pass）完全相同：同一 shader（阈值 _u_Threshold + 曝光 _u_ExposureParams + 颜色矩阵），采样场景图 2132×1198 → 半分辨率输出
金字塔模糊bright-pass → 7 级降采样至 8×4 → 8 级上采样回 533×299，共 15 级额外模糊整体跳过，bright-pass 输出（533×599）直接喂给合成
合成 pass相同 shader：采样场景图（slot 0 _u_BlitTex）+ Bloom 纹理（slot 1 _u_BloomTex）+ 16×16 自动曝光图，_u_Bloom_Params 控制强度/色调
Bloom 内容验证金字塔 16×9 / 8×4 层像素非零（RGB 0–9，较弱但真实参与成像）—
Clear 次数4421（少的主要是金字塔各级的 invalidate）

合成 shader 逻辑（两份截帧一致，SPIR-V 反汇编还原）

bloom = tex(_u_BloomTex, uv) * _u_Bloom_Params.x; // Bloom 纹理 × 强度 color = tex(_u_BlitTex, uv) + bloom * _u_Bloom_Params.yzw; // 场景 + Bloom × 色调 color *= exposure; // 自动曝光（VS 采样 16×16 曝光图，逐像素插值） out = min(color, 16);

结论

  • 泛光确为运行时动态开关：关闭时游戏跳过整棵 15 级模糊金字塔，省 15 个全屏 pass + 15 次 FBO 切换/invalidate；bright-pass 仍保留（兼作自动曝光亮度种子），合成 shader 不变，靠 _u_Bloom_Params 屏蔽贡献。
  • 金字塔各级分辨率都很小（≤533×299，最低 8×4），绝对填充开销不大，主要成本在 pass/FBO 切换次数 —— 对 tile-based 移动 GPU 每次切换都有 tile 写回/失效代价，动态关闭的收益主要在这里。
  • 两份截帧的 DC 总数差异（有泛光 437 vs 无泛光 508）来自战斗时刻场景内容不同，与泛光无关。
  • 注：GL 后端限制（GetConstantBuffer 不可用），无法读取无泛光时 _u_Bloom_Params 的具体数值；但金字塔整体消失已是结构级证据。
